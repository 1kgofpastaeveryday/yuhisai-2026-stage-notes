# iPhone ディマーリモート 設計（2026-10-15 案）

個人用資料。実装は未着手。QLC+ の仕様の確認結果は [LIGHTING.md](../operations/lighting-check/reference.md) 末尾の「iPhoneからディマーを操作する案」。

## 本人の決定（2026-10-15）

- iPhone アプリは Swift、iOS のみ。ローカルネットワーク内だけで使い、サーバーの IP は事前に指定する。
- 会場の照明用 Wi-Fi は専用の SSID とパスワードにする（10/16 本人、仮決め）。SSID は `yuhisai-lighting`、パスワードは `ios/Config/Venue.xcconfig`（git に入れない）にあり、アプリに組み込む（本人「アプリにいれておいてもOK」）。会場のルーター（AX4800）をこの SSID・パスワードに設定する。サーバーから切れている間は「会場照明用Wi-Fiに接続する」ボタンを出し、押すと iOS の確認を経てその Wi-Fi に参加する（Hotspot Configuration、参加した Wi-Fi は保存されて次から自動でつながる）。
- サーバーのアドレスはアプリに直書きせず、iPhone の「設定」アプリの「照明リモート」から変えられるようにする（10/16 本人）。初期値は `<HOST>:8765`。アプリの画面には入力欄を置かない。設定を変えてアプリに戻ると、新しいアドレスにつなぎ直す。
- 操作できるのはディマー（1ch）に限る。1台の iPhone に1ch、1chに1台まで。
- 灯体1台につき操作者を1人置き、各自の iPhone を使ってもらう。
- サーバーは Mac か Windows か未定なので、どちらでも動く言語で組む。
- 小さくてもバックエンドを置く。QLC+ の Web 操作画面は制約が多いため。
- Ableton と iPhone は基本的に同時に使わない。優先度は QLC+ の直接操作 ＞ Ableton ＞ iPhone。
- iPhone を使う枠ではバックエンドを起動し、Ableton を使う枠では止める。止め忘れの対策は、起動中に QLC+ の中と外の画面へ大きく出すこと。
- ムービングの操作も、サーバー側の設定だけで後から有効にできるよう、いま設計しておく。実装はあと（10/16）。ディマーに限るとした 10/15 の決定を広げるもの。下の「ムービングの操作」の節。
- 本番の QLC+ は v5 で、<HOST>の `<PATH>` を使う（10/16 本人）。中身は 5.3.0（f0f302f）に VC ボタン名の修正と Qt の QML ランタイムの差し替えを加えたもので、Web 操作・Simple Desk・スライダー・フレームの部分は 5.3.0 と同じ。5.3.0 のソースで確かめ直し、バックエンドを4点直した（起動方法、値の読み取りの形、ページ折り返しと監視の確認）。このMacにも公式の 5.3.0 を `/Applications/QLC+ 5.app` として入れた（10/16 本人許可、4.14.3 は残した）。
- 会場ネットワーク（10/29 本人決定）：AX4800 を照明リモート専用の LAN（`yuhisai-lighting`、インターネットなし）にする。Mac は Wi-Fi を大学 Wi-Fi のまま、USB LAN アダプタで AX4800 につなぎ、固定 IP `<HOST>`・ルーター欄は空。アプリの既定値と 10/24 に広告研究会へ送った操作案内 PDF（「会場の照明用Wi-Fiに接続する」）はこの形に合う。10/18 に AX4800 を「基本は使わない」とした EQUIPMENT.md の方針と食い違っていたのを、この決定で解いた。広告研究会の iPhone に Tailscale は入れられず、大学 Wi-Fi は端末どうしの通信が規制されているらしい（10/18 本人の見立て）ため。
- インターネット経由の操作（10/29 本人「ローカルじゃなくてネット経由で」「今日の試験もそれで」）：Cloudflare Tunnel `<HOST>`（ingress は `^/ws$` だけ、ほかは404）をバックエンドの公開用の口 `publicListen`（127.0.0.1:8766、iPhone の接続 `/ws` だけ）につなぐ。トンネルからの接続はすべて Mac 内（127.0.0.1）から来たように見えるため、状態ページと割り当ての操作は公開用の口に置かない。アプリの既定のサーバーは `wss://<HOST>/ws` にし、会場照明用 Wi-Fi のボタンはサーバーが LAN のアドレスのときだけ出す（インターネットのない Wi-Fi に入ると公開サーバーに届かなくなるため）。上の AX4800 の決定は LAN に戻すときの手段として残る（設定アプリのアドレスを `<HOST>` にする）。
- 1台の iPhone で最大4台を別々に操作する（10/29 本人「Bです」、照明の名前はサーバーが与える）。プロトコル v2 とアプリの画面は [MULTI.md](MULTI.md)。灯体が1台のときの画面は今までと同じ。
- 端末の本人確認（10/29 本人「IDはサーバーから与える以外できないように」）：画面に出る6文字の ID だけでは、ネット越しに他人がなりすませる。各 iPhone が端末内だけに秘密の鍵を作って接続のたびに送り、サーバーは割り当てのときにその鍵を ID に結びつける。結びついた ID に違う鍵で来た接続は拒否する。Codex（astra）の設計レビューを受けて詰めた内容は MULTI.md の認証の節。
- ムービングのコードはアプリから外す（10/29 本人「捨ててOK」、MULTI.md）。
- 配布ビルドは 1.0.0（3）、最低 iOS は 17.0（10/29 本人「下げても影響がないなら」）。SDK は同じなので iOS 18 以降の端末の動きは変わらない。iOS 17 の端末での動作は未確認（シミュレーターも実機もない）。画面を消さない設定は、前面に戻るたびに入れ直す（10/16 版は起動時の1回だけだった）。
- QLC+ のソースには今後も Codex で手を入れる（10/16 本人）。そのため、5.3.0 で足りない機能（XY パッドを手放す命令など）は QLC+ 側に足す道もある。今回はバックエンド側の工夫（Simple Desk）で済ませた。QLC+ を変えるときの決まりは LIGHTING.md（10/16 本人方針「安定性を厳しく見る」）。バックエンド自体も QLC+ の Web 操作に負荷をかける（灯体ごとに書き込み毎秒最大30回、読み取り毎秒5回）ので、長時間の連続運転試験に含める。

## 構成

```
iPhone（Swift）──Wi-Fi・WebSocket :8765──▶ バックエンド（Go）──localhost・WebSocket :9999──▶ QLC+ ──USB-DMX──▶ 会場ディマー
```

- QLC+ 5 は `qlcplus5 -w show.qxw` で起動する。v5 には操作モードがなく、VC のスライダーは編集中でも DMX を出す（4.14.3 では `-p` が必要だった）。9999番は OS のファイアウォールで LAN からの受信を止め、iPhone がバックエンドを通らずに QLC+ を操作できないようにする。同じマシン内からの接続は止まらない。
- バックエンドは Go で書く。Windows 用と macOS 用の実行ファイルを1つずつ作れば、どちらのマシンにもランタイムを入れずに置ける。Swift は Windows での実行環境が弱く、Node や Python は両方のマシンに実行環境が要る。
- サーバーの IP は、使うマシン側に AX4800 の DHCP 範囲外の固定 IP を手で設定する。Mac と Windows のどちらを使っても同じ IP になり、アプリ側は変えなくてよい。
- QLC+ には灯体ごとに、そのディマー1chだけを割り当てた Level モードの VC スライダーを1本置く（Solo Frame の外）。バックエンドはこのスライダーを `<スライダーID>|<0〜255>` で動かす。

## 優先度の実現

QLC+ は明るさを「高いほうが勝つ」（HTP）で合成するので、優先度はそのままでは表せない。3段をそれぞれ次の方法で作る。

### QLC+ の直接操作が最上位

QLC+ の仕組みだけで成り立つ。Simple Desk で動かした値は、上書きの印を付けて最優先で書かれ、Ableton のシーンと iPhone 用スライダーに勝つ（4.14.3 と 5.3.0 で同じ）。チャンネル監視を有効にした VC スライダーも上書きになるが、v5 では Web から値を変える書き込みをしただけでも上書きになる（同じ値の書き込みでは変わらない、10/16 本物の 5.3.0 で確認）。そのため iPhone 用スライダーは監視をオフにする（オンだと Ableton に勝ち、止めたあとも0で固定される）。バックエンドは監視がオンなら警告を出す。

### Ableton ＞ iPhone はバックエンドの起動・停止で切り替える

本人案（10/15）：iPhone を使う枠ではバックエンドを起動し、Ableton を使う枠では止める。起動したことが「iPhone に渡した」ことになる。専用のボタンは置かない。

| 状態 | iPhone |
|---|---|
| バックエンドを起動した | 0から操作できる |
| バックエンドを止めた | 操作できない |

- iPhone の値はバックエンドではなく QLC+ の VC スライダーに残る。そのため、止めただけでは iPhone で点けた明かりが消えない。バックエンドは起動時と終了時に iPhone 用スライダーを全部0にする。Ctrl+C、ウィンドウを閉じる、ログオフで終了した場合は0に戻す。強制終了や異常終了では戻らないので、その場合は起動し直してから止める。
- 止め忘れたまま Ableton を始めても、バックエンドは iPhone を止めない（本人判断、10/15）。その場合は Ableton と iPhone が「高いほうが勝つ」で混ざり、iPhone で点けた明かりは Ableton の暗転でも消えない。これを防ぐために、起動している間は画面に大きく出す。

### 起動中の表示（QLC+ の中と外）

- QLC+ の中：VC に2ページのフレーム（ページの折り返しなし、ヘッダー非表示）を置く。1ページ目は空、2ページ目は赤背景・大きな文字のラベル「iPhone 稼働中　Ableton の前にサーバーを止める」。バックエンドは起動時に `<フレームID>|NEXT_PG`、正常終了の直前に `<フレームID>|PREV_PG` を送る。端のページでは何も起きないので、今のページを知らなくても同じ結果になる。起動中は数秒ごとに送り直す。異常終了すると赤いまま残るが、iPhone の値も残っているので表示として正しい。
- QLC+ の外：バックエンドの画面を常に最前面に出し、起動中は赤く「iPhone 稼働中」と出す。作り方はバックエンドの言語で決まる（未決）。

### iPhone を操作できる間に QLC+ を直接触った場合

- Simple Desk などで上書きされている間は、iPhone を動かしても光は変わらない。バックエンドは実際の値（`QLC+API|getChannelsValues`）と iPhone の値を毎秒5回ほど比べ、違っていれば iPhone に「照明卓の操作が優先されています。」と出す。
- iPhone 用スライダーそのものを QLC+ で動かした場合は、その灯体の iPhone 操作を止め、「照明卓で直接操作されています。」と出す。バックエンドを起動し直すと戻る。
- グランドマスターは比較に使う値のあとでかかるため、この方法では見つけられない。

## バックエンドの役割

1. 割り当て（本人決定 10/15：誰がどの灯体を操作するかは、iPhone 側ではなくサーバー側で決める）
   - 設定ファイル `config.json` に、灯体名・ディマーch・VC スライダーID を灯体ごとに書く。
   - 各 iPhone はアプリが最初に作る端末ID（英数字6文字、Keychain に保存）で見分ける。IP アドレスは DHCP の払い出しや iOS のプライベート Wi-Fi アドレスで変わることがあるので、見分ける鍵にはせず表示だけにする。
   - 割り当ては `assignments.json` に保存する。1台に1灯体、1灯体に1台まで。
   - 未割り当ての iPhone もつながったままにし、サーバー側の一覧に出す。担当者が一覧から灯体を割り当てると、その iPhone にすぐ反映される。解除しても光の明るさは変えない。
   - 割り当てと解除は、同じマシンからのコマンド（`remote-dimmer devices` / `assign` / `release`）と状態ページのボタンで行う。ホスト用 iPhone から割り当てる案は作らない（下の節）。
2. iPhone 側の WebSocket（JSON）
   - `hello {code, device}` に `assigned {fixture, level, on, active, overridden, qlc}` か `rejected {reason}` を返す。`active` は iPhone から操作できるか（QLC+ 未接続か、直接操作でロックされると false）、`overridden` は実際の光が iPhone の値と違うか、`qlc` は QLC+ との接続状態。
   - `set {level, seq}` で明るさを変える。`seq` が古いものは捨てる。`active` が false の間は捨てる。上書き中は受け付ける（光に出ないことがあるが、上書きが外れればその値が効く。前のシーンが残っている場合も iPhone から明るくはできる）。
   - `on` は直前の0でない値（なければ最大）に戻し、`off` は0にする。直前の値はサーバーが持つ。
   - どれかの値が変わったら `state {level, on, active, overridden, qlc}` を送る。正常終了の前に `shutdown` を送る。
   - 2秒ごとに ping を送る。
3. QLC+ 側
   - 値はスライダーごとに最新値だけを残し、毎秒30回までに間引いて送る（DMX の送出と同じ周期）。
   - 起動中の表示のフレームを2ページ目にしておく。
   - QLC+ との接続が切れたら iPhone に知らせ、1秒ごとにつなぎ直す。つながるたびに全灯体の現在値を送り直す（起動直後は全部0）。
4. 起動時と `.qxw` が保存されるたびの確認。設定ファイルのスライダーが存在するか、Level モードでディマー1chだけを持ち、そのchが設定のアドレスと一致するか、下限0・上限255か、起動中の表示のフレームが2ページで折り返しなしかを確かめる。違えばログと状態ページに出すだけで、止めはしない。
5. 状態ページ（HTTP `/status`）。iPhone を操作できるか（止めた理由）、灯体ごとの接続中の端末、現在値、上書きの有無を出す。
6. ログ。誰がいつどの値にしたか、iPhone がいつ何で止まったかを残す。

## 切断したときの動き

| 起きること | 動き |
|---|---|
| iPhone の Wi-Fi が切れる、アプリが裏に回る | 値は最後のまま残る。アプリは前面に戻るとつなぎ直し、現在値を読み直す |
| バックエンドが落ちる | QLC+ のスライダーは最後の値のまま残る。iPhone で点けた明かりも消えないので、起動し直してから止めると0に戻る |
| QLC+ が落ちる | 照明全体が止まる。既設卓へ差し替える（EQUIPMENT.md 9節） |
| <HOST> が落ちる | 同上 |

## iPhone アプリ

- 表示する情報（本人案 10/15）：この iPhone のローカル IP、端末ID、サーバーのアドレス、割り当てられた灯体、サーバーから切断されているか。iPhone 側で入力するものはない。
- 操作画面（本人指示 10/16）：割り当てられると、画面全体（ステータスバーとホームバーの下まで、余白なし）が1本のスライダーになる。ボタンは置かない。
  - 明るさは、灯体名と%表示の下から端末ID・IPの欄の上までの、画面の幅いっぱいのバーに出す（本人が実機の画面に印を付けて指定、10/16）。画面の上端は通知センター、下端はホームに戻る操作とぶつかるので、バーを端まで伸ばさない。
  - 操作は灯体ごとにサーバーの設定 `faderMode` で選ぶ（本人指示 10/16）。
    - `relative`（既定）：画面のどこでも上下にドラッグすると、指を動かした量だけ明るさが変わる。バーの高さぶん動かすと0から100%なので、塗りが指とぴったり同じだけ動き、触れても明るさは飛ばない。画面のどこでもタップでオン/オフ。本人「一番直感的」（10/16）。iPhone 18 Pro ではバーが約500pt（約8cm）で、本人が先に選んだ感度（画面の高さいっぱいは鈍い、300ptは敏感すぎる、500ptがよい）とほぼ同じになる。
    - `absolute`：バーの中で触れた高さがそのまま明るさになる（触れた瞬間に飛ぶ）。本人「スピードほしいから」。バーの外をタップでオン/オフ。持ち直したときの誤タッチでも光が変わる点は承知のうえ。
  - タップでオン/オフ。オフは0、オンは直前の0でない値（なければ最大）。1回のタップで切り替える。持ち直したときの誤タップで消灯・点灯しうるのでダブルタップも候補だったが、本人が実機で試して「いまのところとくに問題ない」（10/16）ので1回のタップのままにする。
  - 上の情報は全部スライダーの上に重ねて常に出し、タッチには反応させない。灯体名・ch・%は上、端末ID・IP・サーバーは下。
  - 塗りは暗いアンバー（#8A4F0E）。画面全体が塗りになるので、白文字のコントラスト（5.7:1）と、暗い客席で画面がライトにならないことを優先した。
  - 画面の端から始めたスワイプは1回目をアプリが受ける（`defersSystemGestures`）。ホームに戻る操作・通知センターとぶつからないようにするため。実機では未確認。
- 未割り当ての画面：スライダーは出さず、端末IDを画面幅の95%の大きさで出す（本人指示 10/16）。IP とサーバーは下に出す。「未割り当て」の文字や説明文は出さない（スライダーがないことで分かる）。
- `active` が false の間はスライダーを灰色にして操作を受け付けない。上書き中は操作できるまま帯を出す。
- 文言（本人指示 10/16）：画面で説明しない（[artouc/stop-describing-ui](https://github.com/artouc/stop-describing-ui)）。操作者には QLC+ を「照明卓」と呼ぶ。上部の「サーバー接続中」「QLC+」の表示は廃止した。QLC+ が動いているかはクライアントが関知することではなく、サーバーにつながるかどうかが見えれば足りるため（本人）。出す帯は次の3つだけ。

  | 状態 | 帯 |
  |---|---|
  | サーバーから切れた（未割り当て画面でも出す） | サーバーから切断されています。 |
  | QLC+ でこの灯体のスライダーを直接触った（ロック） | 照明卓で直接操作されています。 |
  | 実際の値が iPhone の値と違う（上書き中） | 照明卓の操作が優先されています。 |

  QLC+ との接続が切れたときは、スライダーが灰色になるだけで帯は出さない。
- 使っている間は画面を消さない。前面に戻ったらつなぎ直す。
- Info.plist に `NSLocalNetworkUsageDescription` と `NSAllowsLocalNetworking` を入れる。ローカルネットワークの許可は、各 iPhone でリハーサルまでに一度出して許可してもらう。
- 配布は Ad Hoc にする（10/16 本人「それでいいかも」）。TestFlight 外部テストは、アプリ・ビルド2・外部グループ（公開リンク https://testflight.apple.com/join/<REDACTED>）・テスト情報まで用意したが、ベータ版審査への提出が Apple 側の「Beta Contract is missing.」（ENTITY_UNPROCESSABLE.BETA_CONTRACT_MISSING）で止まっている（API でも Web でも同じ、契約同意後も解消せず）。Ad Hoc は、操作者の iPhone をこの Mac にケーブルで一度つないで登録し、そのままアプリを入れる。リハーサルなど操作者が集まる場でまとめて行う。手順は `ios/scripts/` の Ad Hoc 用の書き出し。
- 配布は TestFlight の外部テスト（公開リンク）を第一案にする。内部テストは操作者を App Store Connect のチームに入れる必要があるので使わない。外部テストはメール招待でも公開リンクでも、そのバージョンの最初のビルドにベータ版審査が入る。公開リンクなら操作者のメールを集めなくてよく、漏れてもサーバーで割り当てない限り操作できない。

### 決めたこと

- 操作はトラックパッド式（本人決定 10/16）。指を動かした量だけ光が動き、離すとその場で止まる。ジャイロとスティック式は作らない。
- 横持ちで固定する（ムービングの画面だけ。ID の画面とディマーの画面は縦のまま）。右手の親指で画面のほぼ全体をドラッグして狙い、左手の親指で左端の明るさの帯を動かす。スマホのアクションゲームで右手の親指で視点を動かすのと同じ動きなので、学生には慣れた操作になる。帯を右に置きたい人には、サーバーの設定で左右を入れ替える。
- 倍率は一定で、画面の幅いっぱいのドラッグで動ける範囲の35%動く。左右と上下で別々にサーバーで変えられる。
- 明るさの帯は、上下のスワイプで明るさ、タップでオン/オフ。狙う面はタップに反応させない（指の置き直しで消灯しないように）。
- 指が触れた瞬間に「狙う」か「帯」かを決め、途中で変えない。狙いながら明るさを変えられる。3本目以降の指は無視する。
- 範囲の端に当たると軽く1回振動する。操作できなくなったときは2回振動する。画面には、動ける範囲の中の狙っている位置を点で出す。
- 照明卓が操作を奪ったとき、切断したとき、割り当てが変わったときは、触っている指の操作をその場で打ち切り、指を置き直すまで動かさない。
- リハーサルで必要と分かったときのために、指の速さで倍率を上げる加速と、帯を長押しで切り替える方式を入れておく。どちらも最初は切っておき、サーバーの設定で入れる。
- 作らないもの：ピンチでのズーム、フォーカス、色、プリセット、元の位置に戻す操作、画面の説明。動ける範囲を舞台の中に絞れば、舞台を見ている操作者が光を見失うことはないので、戻す操作は要らない。ズームとフォーカスは照明卓で決めておく。

### QLC+ 側

- パンとチルトは Simple Desk で動かす（16bit、粗と細の4ch）。XY パッドは使わない。QLC+ 5.3.0 には XY パッドを手放す命令がなく、iPhone の枠のあと Ableton の枠で、パン・チルトを含むシーンが止まるたびにムービングが XY パッドの位置へ振れて戻ってしまうため。Simple Desk なら、サーバーを止めるときに1回手放すだけで済み、QLC+ に XY パッドを作る手間もない。
- ディマーは今の灯体と同じく、チャンネル監視をオフにした VC の Level スライダー。
- 動ける範囲（パンとチルトの最小・最大）、左右・上下の反転と入れ替えは、灯体ごとに config.json に書く。範囲は実機で、客席の目線に光が向かないことを確かめてから決める。
- サーバーを起動したとき、ムービングの今の位置を範囲の中に寄せてから操作を受け付ける。止めるときは、明るさを0にしてからパン・チルトを手放す。手放すとパン・チルトは灯体の既定値か次のシーンの値に移る。
- 照明卓（担当者）の約束：サーバーを起動する前と止める前は、ムービングを暗くし、動かすキューを止めておく。ただし止める前には、パン・チルトを決まった位置に置く「待機」のキュー（明るさ0）だけは走らせておく。サーバーが動いている間は Simple Desk が勝つので、待機のキューを先に走らせても何も変わらず、手放した瞬間にその位置へ移る。キューがないと灯体の既定値に移り、試験に使った灯体（Varytec Hero Spot 230）ではパン・チルトとも0、つまり端まで大きく振れた（10/16、本物の QLC+ 5.3.0 で確認）。サーバーが動いている間は、その4ch を Simple Desk で触らない。強制終了したときは、起動し直してから止める（ディマーと同じ）。

### 本番前に確かめること

一番小さい iPhone での横持ちと両手の操作、実機での向きと16bit の細かさ、動きの遅れ（目安は指を動かしてから光が動き始めるまで中央値100ms以内。300msを超えるならボランティアに追いかけ操作はさせない）、Ableton のシーンより Simple Desk が勝つこと、暗いままの起動と手放し、強制終了からの復帰。リハーサルでは操作者1人につき15分ほど取り、持ち方、帯の操作、代役を追いかける練習、照明卓に操作を返す流れを練習する。

## ホスト用 iPhone からの割り当て（作らない、本人決定 10/15）

再検討するときのための記録

- iOS 17 以降の AirDrop は、iPhone どうしを近づけると送信が始まる。ホスト用アプリが共有シートで割り当て用のファイルを渡し、受け取った操作者のアプリがそれを開く形なら、この動きを使える（本人指摘）。NameDrop の連絡先交換と iPhone どうしの NFC はアプリからは使えない。
- Nearby Interaction（UWB で2台の距離を測る）でも近づけた瞬間を検出できるが、UWB のない機種では使えず、両方の画面で許可が要る。
- どの方法でも、ホストが LAN 越しに割り当てるには、ホストだけが持つ合言葉が別に要る。
- バックエンドの割り当て処理は1か所にまとめてあるので、足すならその処理を呼ぶ入口を増やすだけで済む。
