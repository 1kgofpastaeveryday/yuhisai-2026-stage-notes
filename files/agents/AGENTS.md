# AGENTS.md：小講堂のステージ準備を手伝う AI エージェントへ

この文書は、AI エージェント（Claude Code、Codex など）に、学園祭の小講堂ステージの準備を手伝わせるときに読ませる指示です。雄飛祭2026で実際に起きた失敗から作りました。各項目の後ろの括弧は、その項目ができた理由です。リポジトリの直下に `AGENTS.md`（Claude Code なら `CLAUDE.md` から読み込む）として置いて使ってください。詳しい経緯は https://1kgofpastaeveryday.github.io/yuhisai-2026-stage-notes/ にあります。

## 会場の前提

- 学生の車は構内に入れず、路上にも止められない。搬入と搬出は、近くの駐車場から人の手で行う。
- コンセントは、まとまった1回路あたり10Aまで。消費電力は銘板の値で計算し、「たぶん大丈夫」で済ませない。
- 大学の Wi-Fi では、端末どうしが通信できない場合があり、特定のポートが制限されている。本番の操作は、持ち込んだルーターの中だけで完結させる設計にする。
- 客席の照明（客電）は、既設の調光卓の物理スイッチでしか操作できない。パソコンからの照明の制御だけで本番が回るという前提を立てない。
- 大学との連絡は、必ず実行委員会を通す。

## 外部への連絡

- 業者、実行委員会、出演団体に、エージェントが自分から送信しない。送るのは、担当者が本文を読み、「送って」と明示したときだけにする。会議メモの「今日のうちに見積依頼」のような予定は、送信の指示ではない。（AI がメモを指示と読み違え、条件を詰める前の見積依頼を業者に送った。）
- 下書き、送信予約、送信済み、相手の返事を、台帳で別の状態として持つ。下書きを「送信済み・返信待ち」と書かない。（未送信の連絡を送信済みと記録した。）
- 台帳に記録がないことを「未送信」の根拠にしない。送信トレイやスクリーンショットで確かめてから書く。（送信済みの連絡を未送信として急がせた。）
- 返信を書く前に、元のメールやメッセージを直接読む。返信先のスレッド、文体、相手がすでに答えた内容を確かめる。（企画書ですでに聞いていた質問を「まだ聞いていない」と案内した。）
- 依頼文には、機材名、数量、利用日、受取と返却の日時、まだ決まっていない条件を書く。決まっていないことを「固まった」と書かない。
- 連絡文は、相手が答えるべきことと期限に絞る。（確認事項を全部入れて約2,000字になった。）
- 文面に入れた日付、締切、約束は、送った時点で約束になる。守れない約束は書かない。送ったら台帳に入れる。

## 日付と期限

- 受取日などを変えたら、申込、追加、無料で取り消せる期限を、営業日と受付時刻まで含めてすぐ計算し直す。（受取日を早めたのに無料キャンセル期限が古いままで、取消料50%の日を無料と書きかけた。）
- 料金は、品目、日数、税込みか税抜きかを組にして扱う。（1日料金を2日分と読み違えた。）
- 業者の案内ページは最後まで読む。要約や前半だけで判断しない。到着の目安の時刻と、受付の締切を区別する。（ページ後半の24時間受付を見落とし、返却時刻を誤って案内した。）

## 報告する前に確かめること

- 「起動した」「開始した」と報告する前に、プロセスの実際のログで、処理が続いていることを確かめる。依頼書を置いただけ、起動直後に止まった、を「開始済み」と言わない。
- サーバー機能は、画面の「Started」表示ではなく、ポートが実際に待ち受けていて、外から送って応答が返ることまで確かめる。（QLC+ が開始と表示していたのに、Web 接続を待ち受けていなかった。）
- 保存ファイルの中身と、いま動いているアプリの状態を、別々に確かめる。（ファイルにある機能が、起動中の Ableton Live では欠けていた。）
- 管理画面は、表示を見るだけでなく、人が実際に行う操作を最後まで試す。（毎秒の自動更新でプルダウンが閉じ、操作できなかった。）
- 再生の停止と再開は、カーソルを直接動かして済ませず、実際に再生して停止点を通過させて確かめる。
- 機材の仕様は、記憶やレビュー記事ではなく、メーカーの説明書と実機のスイッチで確かめる。実機にない調整を計画に入れない。（サブウーファーの切り替え周波数を変えられると誤って助言した。）
- 確かめていないことを、保証のように書かない。「32bit float なら音割れしない」「AirTag を2個付ければ十分」のような断言をしない。

## ファイルと版

- 制作ファイルの正本（マスター）の置き場所を最初に1か所に決め、作業用のコピーをあちこちに作らない。
- QLC+ のファイルを Mac で保存すると、入出力の設定が Mac 用に書き換わる。本番の Windows に持っていく前に、出力の設定と割り当ての差分を確かめる。
- 削除する前に、Git で追跡されているか、元に戻せるかを確かめる。（未追跡のファイルを消した後、比較用のスクリプトが動かなくなった。）
- 他の団体のファイルに書き込みが及ぶテストは、隔離した環境で実行する。
- Git の commit に失敗したら、その後の push や公開の処理を止める。（commit 失敗のまま処理が続き、空の値でブランチの削除要求を出しかけた。）
- 並行して編集されている環境で検証するときは、開始と終了時のハッシュを記録する。
- 複数の団体のファイルを1つに統合するときは、ID、テンポ、拍子、出力の割り当てを付け替えた後、呼び出される照明シーンを全件照合する。

## 照明と音

- 照明のタイミングは、音を聞きながら確かめる。小節に機械的にそろえた後も、通して聞く。（自動整列で最大10拍ずれた。）
- フェードの長さ、点滅の頻度、拍の表か裏かを、それぞれ担当者に確かめる。「2小節かけてフェード」を瞬時の切り替えで作らない。
- 照明は、人が直しやすい単位で作る。1曲を1つのクリップにまとめる。（シーンごとに細切れにして、編集しにくいと指摘された。）
- 音量の調整は、測定マイクの音圧（SPL）の数値を見ながら行う前提で手順を書く。耳だけで合わせない。
- 本番の開始ボタンでメトロノームを必ず切る。撮影の開始も、同じボタンで始まるようにできないか検討する。（本番でメトロノームを鳴らし、撮影を始め忘れた。）

## 委任とプロセス

- 長時間の作業を別のエージェントに任せるときは、標準入力を閉じて起動する（例：`codex exec "..." < /dev/null`）。（入力待ちのまま3日間止まっていた。）
- 数日で消える一時フォルダを作業場所にしない。
- 任せた直後に、指定したモデルで動いているか、ログが進んでいるかを確かめる。その後も、ログの更新が止まっていないか定期的に見る。
- ツールの実行が拒否されたことと、担当者に承認画面が出ていることを区別する。存在を確かめていない許可ダイアログを、担当者に探させない。
- 画面操作の停止、接続のリセット、プロセスの終了を区別して報告する。

## 担当者を守る

- 担当者が寝ると言ったら、進捗の通知を送らない。結果はファイルにためる。（就寝後も通知を送り続けて起こした。）
- 眠気があるときは運転をやめる、という条件を、時間短縮の提案で崩さない。
- 担当者1人で受けきれない作業を、引き受ける前提で提案しない。

## 公開する前に

- 公開や push の前に、対象の全ファイルについて、連絡先、個人名、パス、ホスト名、IP アドレスが混ざっていないかを機械的に検査する。過去の版にも残っていないか確かめる。
- 費用分担の資料には、計算に要る情報だけを載せる。
- 手元で直したことと、公開先に反映されたことを別々に確かめる。公開先のページで、数字や団体数を直接見る。
